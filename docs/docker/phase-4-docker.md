# Phase 4 — Docker: 진행 기록과 설명

> 이 문서는 `docs/deploy-guide.md` 의 **Phase 4** 를 실제로 진행하면서 무엇을 만들었고 왜 그랬는지를
> 나중에 혼자 다시 할 수 있도록 자연어로 풀어 쓴 것이다. 파일 안의 실제 내용(코드)은 저장소의 파일을
> 직접 보면 되고, 여기서는 "그게 왜 거기 있는지"만 설명한다.

---

## 1. Phase 4 가 목표하는 것

한마디로: **Paperstock 을 내 PC 어디서든 똑같이 뜨는 "상자(컨테이너)" 두 개로 포장한다.**

- 상자 A = **프론트엔드**: React 앱을 미리 빌드해서 정적 파일로 만든 뒤, 그걸 나눠주는 작은 웹서버(nginx)와 함께 담는다.
- 상자 B = **백엔드**: Express 서버(시세 조회·거래 체결 API)를 Node 실행 환경과 함께 담는다.

그리고 `docker compose up` 한 줄로 두 상자를 동시에 띄워, 브라우저에서 로그인부터 거래까지 되는지 확인한다.

데이터(로그인 계정, 보유 종목 등)는 Firebase 라는 외부 서비스에 있으므로 **상자는 두 개뿐**이다.
데이터베이스 상자는 만들지 않는다.

이 단계는 **전부 내 PC 안에서 끝난다.** AWS 도, 인터넷 배포도, 돈도 개입하지 않는다.
목적은 "이 앱은 컨테이너로 돌아간다"는 사실을 만들어 두는 것. 이후 모든 단계(자동 빌드, 서버 배포)가
여기서 만든 상자를 재료로 쓴다.

---

## 2. 왜 Docker 를 먼저 하나

배포 자동화(GitHub Actions), 서버(AWS), 오케스트레이션(k3s) 셋 다 **"완성된 컨테이너 이미지"가 있다는 전제**
위에서 동작한다. 이미지가 없으면 자동으로 빌드할 것도, 서버에 올릴 것도 없다.
그래서 순서가 **Docker → GitHub Actions → AWS → k3s** 이고, 지금은 그 첫 칸이다.

## 3. 이번에 새로 만든 파일 6개

기존 소스 코드(`src/`, `server/src/`)는 **한 줄도 건드리지 않았다.** 아래 파일만 새로 추가했다.

| 파일 | 한 줄 설명 |
|---|---|
| `Dockerfile` (루트) | 프론트엔드 상자를 만드는 조립 설명서 |
| `nginx.conf` (루트) | 프론트 상자 안 웹서버가 주소를 처리하는 규칙 |
| `.dockerignore` (루트) | 프론트 상자에 넣지 말 것 목록 (비밀·용량) |
| `server/Dockerfile` | 백엔드 상자를 만드는 조립 설명서 |
| `server/.dockerignore` | 백엔드 상자에 넣지 말 것 목록 |
| `docker-compose.yml` (루트) | 두 상자를 한 번에 띄우는 지휘서 |

### 3-1. `Dockerfile` — 프론트엔드 조립 설명서

프론트는 **두 단계로 나눠서** 만든다. 이게 "멀티스테이지 빌드"다.

- **1단계 (빌드용 작업대):** Node 가 깔린 큰 이미지를 임시로 쓴다. 여기서 의존성을 설치하고
  `React 소스 → 정적 HTML/JS/CSS` 로 컴파일한다. 이 작업대에는 TypeScript 컴파일러, Vite,
  수백 MB 의 `node_modules` 가 다 올라간다.
- **2단계 (실제 출고품):** nginx(초경량 웹서버)만 든 작은 이미지를 새로 시작하고,
  1단계에서 나온 **결과물(정적 파일)만** 복사해 넣는다. 컴파일러도 `node_modules` 도 안 가져온다.

**왜 이렇게 하나?** 최종 상자에 빌드 도구가 남아 있으면 용량이 몇 배로 커지고,
쓰지도 않는 프로그램이 잔뜩 들어간 만큼 보안 표면도 넓어진다. "요리는 큰 주방에서, 배달은 도시락만"

이 파일에서 신경 쓴 두 가지:

1. **`postinstall` 훅 제거 후 설치.** 이 저장소는 루트에서 의존성을 설치하면 자동으로
   `server` 쪽 의존성까지 설치하도록 되어 있다(`postinstall` 스크립트). 그런데 프론트 상자에는
   `server` 폴더를 일부러 안 넣기 때문에, 그대로 두면 설치가 "server 폴더가 없다"며 실패한다.
   그래서 설치 직전에 이 자동 훅만 떼어낸 뒤 설치한다.
   *"모든 스크립트 끄기"로 처리하지 않은 이유:* Vite 가 내부적으로 쓰는 `esbuild` 는 설치 스크립트로
   자기 실행 파일을 내려받는다. 스크립트를 통째로 끄면 그게 안 돌아서 빌드가 깨진다.
   그래서 **문제가 되는 훅 하나만** 제거한다.

2. **프론트 환경값 8개를 빌드 재료로 주입.** 아래 4번 개념 설명 참고.

### 3-2. `nginx.conf` — 주소 처리 규칙

React 앱은 "한 페이지짜리 앱(SPA)"이다. 실제 파일은 `index.html` 하나뿐이고,
`/app/portfolio` 같은 주소는 브라우저 안에서 JavaScript 가 가짜로 만들어 보여준다.

문제: 사용자가 `/app/portfolio` 에서 **새로고침**을 누르면, 브라우저는 서버에
"`/app/portfolio` 파일 주세요"라고 진짜로 요청한다. 그런 파일은 없으므로 nginx 는 기본적으로 **404** 를 뱉는다.

그래서 이 설정에 **"요청한 파일이 없으면 무조건 `index.html` 을 돌려줘라"**는 규칙 한 줄을 넣는다.
그러면 앱이 다시 떠서 주소를 보고 알아서 올바른 화면을 그린다.
이 한 줄이 없으면 "직접 접속·새로고침하면 깨지는" 흔한 버그가 생긴다.

### 3-3. `.dockerignore` 두 개 — 넣지 말 것 목록

상자를 만들 때 Docker 는 해당 폴더의 파일을 통째로 복사해 재료로 삼는다.
그중 들어가면 안 되는 것들을 여기 적어 **복사에서 제외**한다.

- **비밀 파일** (`.env`, `.env.local`): Firebase 키 등 민감정보. 이미지에 박히면 이미지를 받은 사람이
  다 볼 수 있다. 절대 금지.
- **`node_modules`**: 내 PC 에 이미 설치된 것. 상자 안에서는 상자에 맞는 버전으로 새로 깔아야 하므로
  가져가면 오히려 방해되고 용량만 크다.
- **`dist`, 로그, 에디터 설정** 등: 결과물·잡동사니. 재료가 아니다.
- 프론트 쪽에서는 **`server` 폴더 전체**도 제외한다. 프론트 상자엔 필요 없다.

### 3-4. `server/Dockerfile` — 백엔드 조립 설명서

백엔드도 두 단계다.

- **1단계:** 모든 의존성을 깔고 TypeScript 를 JavaScript 로 컴파일한다(`dist` 폴더 생성).
- **2단계:** 깨끗한 Node 이미지에서 **운영에 필요한 의존성만** 다시 설치하고(개발용 도구 제외),
  1단계 결과물(`dist`)만 복사한다. 그리고 "4000번 포트로 서버를 켠다"고 지정한다.

개발용 의존성(타입 정의, 테스트 러너 등)을 최종 상자에서 빼는 이유는 프론트와 같다. 작게, 필요한 것만.

### 3-5. `docker-compose.yml` — 두 상자 지휘서

"backend 상자와 frontend 상자를 이렇게 만들고, 포트는 이렇게 연결하고, 환경값은 이렇게 넣어라"를
한 파일에 적어 둔 것. 이게 있으면 명령 한 줄로 둘 다 뜬다.

- **backend:** `server/.env` 파일을 그대로 상자 안 환경값으로 넣는다(Firebase 자격증명, 허용 출처 등).
  내 PC 의 4000번 포트를 상자의 4000번에 연결한다.
- **frontend:** 상자를 만들 때 환경값 8개를 **빌드 재료로** 넘긴다(아래 4번).
  내 PC 의 5173번 포트를 상자 안 nginx 의 80번에 연결한다. 그래서 브라우저에서 `localhost:5173` 으로 본다.

## 4. 꼭 이해하고 넘어갈 개념: "프론트 환경값은 빌드 때 굳는다"

백엔드는 상자를 **켤 때** 환경값을 읽는다. 그래서 같은 상자라도 넣는 값에 따라 동작이 달라진다.

**프론트는 다르다.** React 앱은 빌드하는 순간 `VITE_API_BASE` 같은 값이 **결과 파일 안에 문자열로 그대로
박혀서 굳는다.** 나중에 바꿀 수 없다. 이미 구운 쿠키에서 설탕을 빼낼 수 없는 것과 같다.

그래서:

- 지금(로컬)은 `VITE_API_BASE = http://localhost:4000` 을 박아서 굽는다.
- 나중에 실서버에 올릴 이미지는 `VITE_API_BASE = https://ps.<서버주소>.nip.io` 를 박아서 **따로 굽는다.**
- 즉 환경마다 **프론트 이미지를 새로 빌드**한다. 소스 코드는 그대로 두고, 빌드할 때 넘기는 재료만 바꾼다.

주입하는 값 8개 (전부 `.env.local` 에 이미 있음):

1. `VITE_API_BASE` — 백엔드 API 주소
2. `VITE_FIREBASE_API_KEY`
3. `VITE_FIREBASE_AUTH_DOMAIN`
4. `VITE_FIREBASE_PROJECT_ID`
5. `VITE_FIREBASE_STORAGE_BUCKET`
6. `VITE_FIREBASE_MESSAGING_SENDER_ID`
7. `VITE_FIREBASE_APP_ID`
8. `VITE_FIREBASE_MEASUREMENT_ID`

2~8 은 Firebase 클라이언트 접속 정보다. 이게 빠지면 앱 화면은 떠도 로그인이 아예 초기화되지 않는다.

> **참고 (자주 하는 오해):** 이 값들은 원래 브라우저에 노출되는 공개 설정값이다. 진짜 비밀은
> 백엔드의 `FIREBASE_PRIVATE_KEY` 이고, 그건 `server/.env` → 백엔드 상자에만 들어간다.

## 5. 실행 방법

Docker Desktop 이 켜져 있어야 한다(트레이 아이콘/좌하단 초록불).

저장소 루트에서:

```
docker compose --env-file .env.local up --build
```

- `--env-file .env.local` : compose 가 프론트 빌드 재료 8개를 `.env.local` 에서 읽게 한다.
  이걸 빼면 값이 비어서 프론트가 잘못 빌드된다.
- `--build` : 이미지를 (다시) 만든 뒤 띄운다. 파일을 고쳤을 때 필요. 처음엔 무조건 필요.
- 처음 실행은 의존성 설치 + 빌드 때문에 몇 분 걸린다. 두 번째부터는 캐시 덕에 빠르다.

끄기: 터미널에서 `Ctrl + C`, 그다음 `docker compose down` (상자 정리).

## 6. 검증 체크리스트

1. **백엔드 헬스체크**
   브라우저나 다른 터미널에서 `curl http://localhost:4000/health`
   → `{"status_code":200, ... "data":{"status":"ok"}}` 가 나오면 백엔드 상자 정상.

2. **프론트 화면**
   브라우저에서 `http://localhost:5173` → 랜딩 페이지가 뜬다.

3. **로그인 → 앱 진입**
   회원가입 또는 로그인 → `/app/portfolio` 로 들어가진다. (Firebase 연결 정상 확인)

4. **새로고침 404 없음**
   `/app/portfolio` 화면에서 브라우저 새로고침 → 그대로 화면이 유지된다(404 아님).
   → `nginx.conf` 의 규칙이 동작한다는 뜻.

5. **시세·거래**
   Markets 화면에서 종목 시세가 보이고, 매수/매도가 처리된다.
   → 프론트 ↔ 백엔드 ↔ Firebase 왕복이 다 된다는 뜻.

다섯 개 다 통과하면 Phase 4 완료.

## 7. 자주 나는 문제와 원인

| 증상 | 원인 / 확인할 곳 |
|---|---|
| 프론트 화면은 뜨는데 로그인 버튼이 아무 반응 없음 / 콘솔에 Firebase 에러 | 빌드 재료 8개 중 `VITE_FIREBASE_*` 가 안 들어감. `--env-file .env.local` 빠뜨렸는지 확인 |
| 로그인 시도 시 네트워크 에러 / API 호출이 엉뚱한 곳으로 감 | `VITE_API_BASE` 가 안 박힘. 위와 동일 원인 |
| 앱 화면에서 새로고침하면 404 | `nginx.conf` 가 이미지에 안 들어갔거나 규칙이 잘못됨 |
| 브라우저 콘솔에 CORS 차단 메시지 | `server/.env` 의 `CORS_ORIGIN` 이 `http://localhost:5173` 이 아님. 프론트를 보는 주소와 정확히 같아야 함 |
| `docker compose up` 이 "server 폴더 없음" 류로 설치 실패 | 프론트 `Dockerfile` 의 postinstall 훅 제거 단계가 빠짐 |
| 첫 빌드가 너무 느림 | 정상. 의존성 설치 + 컴파일. 두 번째부터 빨라짐 |
| 포트 충돌(5173/4000 already in use) | `npm run dev` 등 기존 프로세스가 그 포트를 쓰는 중. 끄고 다시 |

## 8. 다음 단계 예고 — Phase 5 (GitHub Actions CI)

Phase 4 로 "손으로 상자를 만들 수 있다"가 됐다.
Phase 5 는 그걸 **자동화의 앞단**만 붙인다: `main` 에 푸시하거나 PR 을 올리면 GitHub 이 알아서
빌드·린트·테스트를 돌려 "이 코드는 최소한 깨지진 않았다"를 체크한다. (이미지 빌드·배포는 Phase 7)

그 뒤 Phase 6 에서 AWS EC2 + k3s 를 준비하고, Phase 7 에서 지금 만든 이 상자들을
실제로 인터넷에 띄운다.
